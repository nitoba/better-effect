The optional `better-effect/next` entry point adapts an application-owned
Runtime to the native Next.js App Router Route Handler API. It does not import
Next.js from the core or main better-effect entry point.

Install the adapter with Next.js and better-result:

```bash
bun add better-effect better-result next
```

`next` is an optional peer dependency. Only applications that import
`better-effect/next` need it.

## Create a Route Handler

Create the Runtime once during application startup. `NextEffect.gen` exposes
Next's asynchronous route `params` and returns the exact
`(request, context) => Promise<Response>` shape expected by a route file:

```ts
import { Result } from 'better-result'
import { Layer, Runtime, Service } from 'better-effect'
import { NextEffect } from 'better-effect/next'

class UserService extends Service<UserService>()('UserService') {
  find(id: string) {
    return { id, name: 'Ada' }
  }
}

const runtime = await Runtime.make(Layer.make(UserService))
const http = NextEffect.make(runtime)

export const GET = http.gen(async function* (_request, context: RouteContext<'/api/users/[id]'>) {
  const { id } = await context.params
  const users = yield* UserService

  return Result.ok(users.find(id))
})
```

Next generates the global `RouteContext` type when you run `next typegen` (and
also during `next build`). You can use `NextEffect.Context<{ ... }>` when an
application provides its own context type.

Use `handler` when a complete Program already exists:

```ts
import { Effect } from 'better-effect'

const getUser = (id: string) =>
  Effect.fn(async function* () {
    const users = yield* UserService
    return Result.ok(users.find(id))
  })

export const GET = http.handler((request, context) => {
  const id = new URL(request.url).pathname.split('/').at(-1) ?? ''
  void context
  return getUser(id)
})
```

Both forms check the Program's Service requirements against the Runtime Layer.
A missing Service or incompatible request Layer is rejected at the TypeScript
boundary. The `Failure` channel is also checked when a typed `onFailure`
policy is configured.

For a long-lived App Router application, keep the Runtime in an
application-owned module and expose explicit disposal for the host lifecycle:

```ts
// app/runtime.ts
export const appRuntime = await Runtime.make(AppLive)

// Call this from the actual host/server shutdown hook.
export const disposeAppRuntime = (): Promise<void> => appRuntime.dispose()
```

Route modules import that Runtime and bind it to the adapter:

```ts
// app/api/users/[id]/route.ts
import { appRuntime } from '@/app/runtime'

const http = NextEffect.make(appRuntime)
```

Do not put this long-lived Runtime in an `await using` scope that ends during
module initialization; that would dispose it before exported handlers serve
requests. `NextEffect.make` stores only the Runtime supplied by the caller: it
does not create a process-global singleton or mutate hidden adapter state.
Sharing `appRuntime` is an application ownership choice.

## Request context and lifecycle

Each invocation creates exactly one WebEffect execution and child Scope. The
adapter installs `CurrentRequest` and links the native request's
`AbortSignal` to `CurrentAbortSignal`. Request-local providers are created by
`requestLayer` once per request and are released before the returned handler
Promise resolves:

```ts
const http = NextEffect.make(runtime, {
  requestLayer: (request, context) =>
    Layer.scoped(
      RequestId,
      () => new RequestId(request.headers.get('x-request-id') ?? 'missing'),
      (requestId, outcome) => {
        console.log(requestId.value, outcome.status)
        void context
      }
    )
})
```

The Runtime remains application-owned; call `disposeAppRuntime()` from the
actual application/server shutdown hook. Concurrent handlers keep their
request Layers, requests, and route contexts isolated. Root Layer resources
remain owned by the Runtime and are not released at the end of an individual
request.

For a deployment that cannot retain a long-lived Runtime, use the existing
`Runtime.use` helper explicitly around the handler invocation. This opts into
creating and disposing a Runtime for that invocation; `NextEffect` never does
so implicitly:

```ts
export const GET = (request, context) =>
  Runtime.use(AppLive, (runtime) =>
    NextEffect.make(runtime).handler(() => getUser(context))(request, context)
  )
```

The adapter does not add Edge-runtime support. Use it only on hosts supported
by the configured better-effect Runtime.

## Responses and failures

By default, a successful value is returned as `{ data: value }` JSON. A
successful `Response` is passed through unchanged. A route may select at most
one success policy: use `serialize` for a JSON-safe transformation, `respond`
for complete Response control, or route-level `onSuccess` to replace the
shared success policy:

```ts
export const GET = http.gen(
  async function* () {
    return Result.ok(await loadSummary())
  },
  {
    serialize: (summary) => ({ id: summary.id, total: summary.total })
  }
)

export const HEAD = http.handler(() => headProgram, {
  respond: () => new Response(null, { status: 204 })
})
```

Shared policies receive the native request and Route Handler context:

```ts
const http = NextEffect.make(runtime, {
  onSuccess: ({ value }, request, context) =>
    Response.json({ value, method: request.method, context: Boolean(context) }),
  onFailure: (error, request, context) => {
    console.error('request failed', request.url, context)
    return Response.json({ error: 'Request failed' }, { status: 500 })
  }
})
```

`Result.err` uses `onFailure`; without a custom policy, non-Response failures
are redacted to `{ error: 'Internal Server Error' }` with status 500. Thrown or
rejected defects remain rejected rather than being exposed as response bodies.
Response policies may be asynchronous but must return a standards-compatible
Web `Response`. Serialization follows the strict rules documented for
[`better-effect/web`](/docs/web): unsupported values are rejected instead of
silently dropped or coerced.
